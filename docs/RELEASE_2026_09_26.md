# FeedForward — production hardening and 3D frontend

Historical first-pass report. The subsequent changes and latest checks are documented in [DEPLOYMENT.md](DEPLOYMENT.md) and [VERIFICATION.md](VERIFICATION.md).

Source: feedforward-notification-flow-20260911.zip, the latest saved FeedForward source found for this task. This is a hardened release candidate, not a certified or deployed production service. Changes made on your computer after September 11 are not included.

## Architecture reviewed

React 19 + TanStack Start/Router/Query + TypeScript + Tailwind; FastAPI validates API inputs and uses a pooled HTTPX gateway; Supabase handles authentication, PostgreSQL, row-level policies and transactional RPCs. The Supabase publishable key intentionally exists in the browser, so API checks alone do not secure the database. This release strengthens the direct REST boundary too.

## Implemented changes

- Replaced the static landing photo with a CSS 3D food crate and food shapes, perspective, floating motion, donation/delivery/NGO labels, pause/resume, and reduced-motion handling. No WebGL dependency or animation JavaScript loop.
- Replaced claim cancellation's read/patch sequence with a row-locked, idempotent RPC. Scheduled claims must use delivery cancellation. Completed claims cannot be cancelled through this endpoint.
- Added a listing cancellation RPC that rejects listings with reserved quantities.
- Revoked authenticated/anonymous direct mutations of claims, pickups and impact records; revoked direct listing updates/deletes. Transactional security-definer RPCs own these operations.
- Changed nullable volunteer ownership comparisons to `IS DISTINCT FROM`; required volunteer authentication for PIN verification.
- Prevented failed handover PINs from returning already collected food to donor inventory. Collected quantities remain reserved for administrative resolution.
- Added database triggers to prevent ordinary users from self-verifying organisations or inserting already-claimed/completed listings.
- Enforced timezone-aware listing and pickup timestamps, future best-before times, non-future preparation timestamps, and valid route coordinates.
- Excluded expired listings from marketplace API browsing.
- Added request IDs, status/duration logs, generic unexpected-error responses, upstream outage handling and database error sanitisation. Logs omit credentials, request bodies and query strings. Request IDs correlate responses with logs; external error monitoring is still required.
- Tightened production HTTPS upstream and exact-origin validation.
- Corrected the landing page's unsupported live-traffic routing claim; routing is an approximate distance heuristic.
- Added regression tests and a reverse-proxy rate/body/connection-limit example. The example is not enabled automatically and is not a distributed per-user quota system.

## Update on Windows

1. Back up your existing folder and database. Extract this ZIP into a separate folder; copy only your own local configuration into it. Do not overwrite a newer working checkout without comparing changes.
2. From the extracted `meal-link-loop-main` folder:

```powershell
npm ci
npm run check
npm run build
cd backend
py -3.12 -m venv .venv
& .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pytest tests -q
cd ..
```

3. Configure `.env.local` and `backend/.env` using their example files. Frontend: Supabase URL/publishable key, API URL and restricted Ola Maps key. Backend: Supabase URL/publishable key/service-role key and exact frontend origin. Never put a service-role key in a `VITE_` variable.
4. Link a STAGING Supabase project and apply all pending migrations, including `20260926000100_workflow_boundary.sql`:

```powershell
npx supabase login
npx supabase link --project-ref YOUR_STAGING_PROJECT_REF
npx supabase db push
```

5. Run backend and frontend in separate terminals:

```powershell
# Backend, from backend/
& .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# Frontend, from project root
npm run dev -- --host 127.0.0.1 --port 8001
```

Open http://localhost:8001. For production, use the platform's supported TanStack SSR deployment path, HTTPS API hosting, `ENVIRONMENT=production`, exact HTTPS origins, and a trusted reverse proxy. Do not expose the development server publicly. The nginx example requires adaptation to your hosting topology and TLS setup.

## Required staging acceptance tests

Use separate donor, NGO, volunteer, unrelated volunteer and admin accounts, plus a direct Supabase REST client with each user's access token.

| Test | Required result |
| --- | --- |
| Volunteer attempts donation | Denied by API and database |
| Ordinary user sets `verified=true` using REST | Denied |
| Direct REST insert/update of claims, pickups or impact | Denied |
| Direct insert of claimed/completed listing | Denied |
| Two simultaneous claims exceeding availability | One rejected; reserved total never exceeds quantity |
| Two simultaneous volunteers accept one pickup | Exactly one assignment |
| Unassigned/unrelated volunteer advances pickup | Denied |
| Cancel confirmed claim twice | Quantity released exactly once |
| Cancel claim with delivery already scheduled | Rejected; use delivery cancellation |
| Donor cancels listing with live reservation | Rejected |
| Five wrong delivery PINs after collection | Pickup cancelled; collected quantity is not made available again |
| Correct PIN submitted twice | One impact record only |
| NGO views its PIN; volunteer queries PIN table | NGO allowed; volunteer denied |
| Food at expiry boundary | Cannot be claimed or newly scheduled |
| 375 px mobile layout and keyboard navigation | No overflow; visible focus; all controls usable |
| Pause and reduced motion | Illustration stops; primary actions remain usable |
| Supabase unavailable | API returns controlled 503; session not falsely marked expired |

## Remaining public-launch gates

- Apply and exercise the migration on staging, including concurrent operations and full donor → NGO → volunteer → PIN delivery. Review mixed partial-claim listing status behavior under multiple simultaneous deliveries.
- Verify the production Auth redirect allowlist, email confirmation, SMTP and account recovery. Rotate any credentials exposed in older archives (the previous audit records such an exposure).
- Enable external error monitoring, uptime alerts, database backups/PITR and perform a restore drill.
- Configure edge abuse controls at BOTH API and Supabase/Auth boundaries. The supplied proxy example protects only traffic routed through it; clients can call Supabase directly.
- Implement verified file uploads with storage policies; existing external food photo URLs remain a reliability/privacy concern.
- Add a scheduled expiry/reconciliation process and an audited admin process for failed physical handovers. API expiry filtering alone does not perform operational cleanup.
- Run authenticated browser E2E, accessibility, dependency and load tests on your deployment. Review large Ola Maps/Recharts bundles before scaling.
- Review food-handling guidance, contact-data retention, consent and incident response with the platform operator.

Do not announce an unrestricted public launch until these checks have evidence. Migration and backend changes belong in one coordinated release: old cancellation endpoints cannot run after direct table updates are revoked. The migration is transactional. If validation fails before commit it rolls back; after deployment, prefer a reviewed forward fix rather than restoring unsafe table grants. Retain the preceding source version and a database backup for recovery planning.
